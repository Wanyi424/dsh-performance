# 设计说明

0.2.0 由后端开发完成，没有经过产品和设计评审。0.3.0 从用户要回答的问题出发重做了信息结构。0.4.0 根据实际使用的反馈做了两件事：一是三项指标同屏、不再切换；二是补上整机参照、交互延迟、进程趋势和工具进程启停。视觉沿用快捷翻译和 Markdown 笔记的原生风格：界面颜色只取 DSH 主题变量，52px 顶栏，16px 卡片圆角。

## 用户要回答的问题

| 问题 | 页面里的回答 |
| --- | --- |
| 电脑慢，是不是 DSH 造成的？ | 「此刻」两条整机占比条：DSH 的部分、其他程序、空闲一目了然 |
| 是哪一部分、哪个程序在占用？ | 趋势按五个组成部分堆叠；进程表每行带趋势；「此刻」直接点名 CPU 最高、内存最多的进程 |
| 刚才卡的那一下和什么同时发生？ | 三条轨道共用时间轴，一根竖线贯穿全部；工具进程的运行时段画在最下方 |
| Agent 启动的程序在占用吗？ | 工具进程单独成组并计入合计；已退出的程序保留在「已退出」下，同一命令合并 |
| 长时间运行后内存有没有涨？ | 历史保留 1 小时；内存轨道显示「较 N 分钟前」的变化，进程趋势小图看出是谁在涨 |

## 关键取舍

- **联动时间轴，而不是三张卡片切换**：对照同一时刻是诊断的核心。轨道共用横轴；纵轴各自独立（单位不同），从不把两个量画在同一纵轴上。
- **此刻只给整机参照，不重复 DSH 的大数字**：DSH 自己的当前值在各轨道左侧；「此刻」负责回答 DSH 在整台电脑里占多大比重。
- **只陈述事实，不打分**：没有健康评分或「偏高」之类的判断。只列出峰值、变化，以及占用最多的进程。
- **启停行只画在视图内开始或结束的程序**：整段都在运行的程序没有可标记的事件，它们在进程表里。
- **不做的指标**：
  - GPU 占用：PDH 每次要枚举数百个 GPU 引擎计数器，开销远超整套采集；
  - 网络流量：按进程统计需要管理员权限的系统跟踪；
  - 卡顿归因到插件：DSH 把各插件入口合并成一个脚本加载，React 渲染也统一记在 DSH 名下，归因不可靠；
  - 界面 JS 内存：Chromium 默认只给取整、低频更新的值。

## 图表规范

- **配色**：五个组成部分使用一套经过校验的分类色，按堆叠顺序依次分配，浅色、深色主题各一套。校验在 DSH 实际的白色和 `#191c22` 背景上进行，相邻色在色盲模拟下 ΔE ≥ 8.4，正常视觉 ΔE ≥ 19。浅色主题下青、黄、洋红对背景的对比度低于 3:1，因此每个数值都能在提示框和进程表中读到。

  | 组成部分 | 浅色 | 深色 |
  | --- | --- | --- |
  | 界面渲染 | `#2a78d6` | `#3987e5` |
  | GPU | `#eb6834` | `#d95926` |
  | 主进程与服务 | `#1baf7a` | `#199e70` |
  | 后台服务 | `#eda100` | `#c98500` |
  | 工具进程 | `#e87ba4` | `#d55181` |

  卡顿柱与慢交互使用保留的状态色（`#ec835a`、`#d03b3b`），并且始终配有图例文字。
- **标记**：
  - 堆叠面积为淡填充，每个组成部分顶边画一条 1.5px 的线；组成部分为零的地方不画线。
  - 网格线为实线细线；只有 200 ms 阈值线用虚线。
  - 悬停标记 ≥ 8px，带 2px 底色描边。
  - 文字从不使用数据色。
- **提示框**：一个提示框列出所有组成部分，数值在前、名称在后，每行用一小段对应颜色的线作为色键。
- **数字**：大号数字使用比例数字，表格与坐标使用等宽数字。
- **动效**：
  - 没有任何循环动画；
  - 每次读数到达时，状态点和最新数据点各闪一下；
  - 占比条的宽度随数据过渡；
  - 侧边详情滑入、滑出；
  - 减少动态效果模式下全部改为即时完成。

## 交互约定

- 悬停或键盘查看图表时，时间窗口固定，查看的时刻不会滑走。停在没有读数的空档时，提示框不借用相邻的读数。
- 指向任一组成部分（图例、占比条、进程行），所有图表里只突出它；高亮通过根节点上的样式实现，图表不会因此重新渲染。
- 进程表每次读数都会按所选列重新排序；鼠标停在表上时行序保持，新出现的行排在末尾。
- 窄屏：
  - 860px 以下，占比条单独占一行，并隐藏内存占比条；
  - 640px 以下，轨道读数列收窄，峰值时刻标签隐藏，趋势小图压缩。
