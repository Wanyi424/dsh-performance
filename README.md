# DSH 运行监控

Windows 桌面版 DeepSeek Harness 的轻量插件，用来回答五个问题：

- 电脑慢，是不是 DSH 造成的？
- DSH 的哪一部分、它启动的哪个程序在占用资源？
- 刚才卡的那一下是什么时候、和什么同时发生的？
- 长时间运行后，内存有没有一直上涨？
- 哪个插件在占用 DSH 后台的 CPU 和内存？

## 安装

适配 DSH `0.2.0-rc.2`。采集器为 Windows x64 程序，使用系统自带的 .NET Framework 4.x。

在 DSH 左侧「插件」→「添加插件」中选择本地压缩包：

```text
D:\code\plugins\dsh\dsh-performance\dist\dsh-performance-0.5.0.tgz
```

启用后完整退出并重启 DSH。不需要 API Key，不调用模型，也不与 Agent 交互。

## 使用

**侧栏入口**：侧栏底部的「运行监控」一行，右侧实时显示 CPU 和内存合计。点击打开详情页，打开期间该行显示为选中。侧栏收起时只留图标，悬停可看读数。

**详情页**从上到下分为四部分，顶栏可切换时间范围：5 分钟、15 分钟、1 小时。

1. **此刻**：整机 CPU 和内存各用一条横条表示。
   - DSH 占用的部分按组成部分着色：界面渲染、GPU、主进程与服务、后台服务、工具进程。
   - 其他程序显示为灰色，剩余部分是空闲。
   - 下方一行列出此刻 CPU 最高和内存最多的进程，点击可直接打开它的详情。
2. **趋势**：CPU、内存、界面响应三条轨道上下排列，共用一条时间轴。
   - **左侧读数**：每条轨道左侧是当前值和区间统计（平均、峰值、较区间开始的变化）。指向峰值旁的时刻标签，竖线会跳到那一刻。
   - **悬停联动**：鼠标悬停时，一根竖线贯穿三条轨道，提示框列出那一刻各组成部分的 CPU 和内存、DSH 合计以及整机占用。悬停期间时间轴不滚动；方向键可逐点查看。
   - **界面响应轨道**：柱是卡顿的帧，柱高为持续时长；点是点击、按键的响应时间，超过 200 毫秒的标红。
   - **最下方的「工具进程」行**：长时间运行的程序（如开发服务器）画成运行时段条，一次性命令画成短竖线，可以直接对照内存、CPU 的变化。
   - **联动高亮**：指向图例、占比条或进程表中的任一项，所有图表里只突出该组成部分。
3. **进程**：分为「DSH 应用」和「工具进程」两组，每行带所选指标的趋势小图。
   - 工具进程按程序合并子进程。已退出的程序收在「已退出」下，同一命令的多次运行合并为一行，例如「Git × 6」。
   - 点击任一行，右侧打开详情：该进程的 CPU 与内存曲线、它是做什么的、何时启动、线程数、完整命令行（可复制），以及包含的子进程。
4. **插件**：列出已安装的插件（不含 DSH 自带的组合包）。
   - **自带进程**：插件自带的程序（例如本插件的采集器）按所在目录归到对应插件，实时显示 CPU 和内存；它们在进程表里也会标出属于哪个插件。
   - **按插件分析后台**：选择 10、30 或 60 秒后点「开始分析」，结束后列出这段时间后台主线程忙了多久，以及各插件、DSH 内核、垃圾回收各占多少，并给出各自新增且仍占用的内存（估算）。展开插件可看到它最耗时的函数和新增内存最多的位置（文件与行号），展开 DSH 内核可看到最忙的模块。分析期间照常使用 DSH，结果更能反映实际占用；结果保留到下次分析。

窗口不可见时自动暂停采集。采集失败时，页面保留最后一次读数并变淡，显示原因和「重试」，15 秒后也会自动重试。

## 统计口径

从插件所在的后台进程向上，找到最上层的 `DeepSeek Harness.exe`，即桌面主进程。再沿进程树向下，统计：

1. 桌面主进程，以及它的界面渲染、GPU、网络、存储等子进程。进程类型由 Electron 的 `--type` 参数识别。
2. DSH 后台服务，即同一个可执行文件以 Node 模式运行的进程。
3. 后台启动的全部程序及其子孙进程，即「工具进程」，计入合计。

以下不计入：
- 采集器自身的占用，单独显示在页脚，不计入 DSH 合计。
- 父进程已经退出的程序，因为无法确认来源。
- 树外的同名程序。

插件不接受网页传入的 PID 或命令，也不提供结束进程的操作。

指标定义：
- **CPU**：各进程在采样间隔内使用的 CPU 时间之和，除以间隔和逻辑处理器数。100% 表示整台电脑的算力全部占满，与任务管理器一致。两次采样之间启动的进程，其全部 CPU 时间都计入这个间隔；PID 被复用时不沿用旧进程的读数。
- **内存**：进程专用工作集之和，与任务管理器「详细信息」页的「内存(专用工作集)」列一致。需要 Windows 10/11 22H2 及 2023 年 9 月以后的累积更新，不支持时显示 `—`。个别进程没有读取权限时不计入合计，并在「此刻」中注明数量。
- **整机**：CPU 来自 `GetSystemTimes`，与 DSH 用同一个采样间隔计算；内存为已使用的物理内存，即总量减去可用（`GlobalMemoryStatusEx`）。
- **界面响应**：
  - **卡顿**：取自 Chromium 的 Long Animation Frames，即一帧被拖延超过 50 毫秒；不支持时退回 Long Tasks。
  - **交互延迟**：取自 Event Timing，即从点击或按键到界面画出反馈的时间，超过 200 毫秒标红。
  - 两者都由浏览器事件推送，没有轮询，只在窗口可见时记录。打开本页期间，本页自身的绘制也会计入。
- **插件占用**：插件没有自己的进程，全部运行在 DSH 后台进程里（界面部分在界面渲染进程里），系统无法分开计量。分析时，后台在自己进程里通过 `node:inspector` 打开 V8 的 CPU 采样分析器（每毫秒一次）和抽样堆分析器（每分配 32 KB 记一次）。
  - 每个样本归到调用栈上离它最近的插件代码：插件按其安装目录（`~/.dsh/profiles/desktop/node_modules/<插件>`）识别，DSH 安装目录中的代码算作 DSH 内核，并按包细分。
  - 插件同步调用的 DSH 代码算作该插件；插件触发后由 DSH 稍后异步完成的工作（比如等待中的模型请求）不带插件的调用栈，算作 DSH 内核。
  - 只统计后台主线程：文件和网络读写在线程池里，不计入；界面部分不在范围内，因为插件的界面由 DSH 共用的 React 渲染，无法可靠归属。
  - 「新增内存」是分析期间分配、且在结束时的一次完整垃圾回收后仍存活的内存，是抽样估算值。这次垃圾回收可能让后台短暂停顿。
  - 插件列表来自 profile 的 `package.json` 中记录的组合包，去掉 `@deepseek-ai/` 下 DSH 自带的部分；插件名称取自插件的语言文件。
- **程序启停**：根据每次读数推断。启动时间取进程自己的创建时间；退出时间是最后一次看到它运行的时刻。窗口不可见期间启动又退出的程序不会出现。

## 开销控制

- **采样频率**：侧栏常驻读数时每 3 秒一次，打开详情页时每 2 秒一次，失败后每 15 秒一次。两处共用一个采样器。
- **Host 端合并**：并发请求合并为一次，1.8 秒内的重复请求直接复用结果。
- **采集器**：每次请求只读一次进程快照，以及树内各进程的 CPU 时间、内存、线程数和两项整机计数。命令行每个进程只读一次并缓存。不使用 WMI、PowerShell，不扫描文件；闲置 15 秒后退出。
- **历史数据**：只保存在内存中，保留 1 小时，不写磁盘、不上传。
  - 趋势每个读数只存五个分组的汇总。
  - 每个进程和程序的趋势按 15 秒汇总。
  - 已退出的程序最多保留 300 个。
  - 卡顿和交互各最多 3000 条。
- **插件分析**：只在点「开始分析」后运行，时长固定为 10、30 或 60 秒，同一时间只有一次；结束或取消后，分析器立即断开、不再有任何开销。原始采样数据只在后台内存中用于汇总，不传给页面、不写磁盘。
- **页面渲染**：
  - 长时间范围按绘图宽度抽稀，每两个像素约画一个点；统计仍使用全部读数。实测一小时、1800 个读数的统计每次约 0.1–0.2 ms。
  - 页面没有循环播放的动画，只在数据更新或用户操作时短暂动一下。
- **包体**：侧栏入口约 13.5 KB，常驻加载；详情页约 85 KB，打开时才加载；后台部分约 20 KB。复用 DSH 的 React，不引入图表库、组件库或图标库。

0.2.0 曾在本机测得：采集器稳定后约占整机 0.06% CPU，专用工作集约 10 MB；0.3.0 与 0.4.0 的采集器检查中约 5 MB。0.5.0 尚未在真实 DSH 中实测插件分析的开销，可用下文的基准脚本复测常驻部分。

## 开发与验证

```powershell
npm ci
npm run typecheck
npm test
npm run build
npm run check:collector
npm run check:browser
npm pack --pack-destination dist
```

- `npm run build`：用系统自带的 .NET Framework C# 编译器生成 `lib/collector.exe`，发布包同时包含 `native/Collector.cs` 源码。
- `npm test`：单元测试，其中一项在 Node 进程内真实运行 V8 的 CPU 与堆分析器，验证一个模拟插件的忙循环和占用的内存被归到该插件。
- `check:collector`：用一棵隔离的 Windows 进程树验证采集结果，包括：
  - 进程类型识别：主进程、界面渲染、GPU、Host，Host 启动的 Shell 及其子进程；
  - 树外同名程序被排除；
  - 整机计数与线程数的读取；
  - 可执行文件位于插件目录中的工具进程归属到该插件；
  - 并发合并、闲置退出、重建基线与释放。
- `check:browser`：在隔离载体中加载实际构建的界面。请求由 Playwright 拦截应答，不占用端口。
  - 数据：采集读数为脚本化场景，卡顿和慢交互是 Chromium 真实产生的事件。
  - 验证范围：懒加载、选中态、整机占比、三轨联动与提示框、程序启停、联动高亮、已退出程序、侧边详情、排序、插件自带进程与插件分析（分析结果为脚本化数据）、可见性暂停、错误与重试、窄屏和深色主题。
  - 截图保存在 `artifacts/`；需要 Playwright Chromium。

可选：对正在运行的 DSH 做只读实测。参数换成桌面主进程的 PID，即任务管理器「详细信息」页中最上层的 `DeepSeek Harness.exe`：

```powershell
node --import tsx scripts/benchmark.ts <DSH桌面主进程PID>
```

## 文件结构

```text
native/Collector.cs    Windows 只读采集器：沿进程树读取 CPU 时间、内存、线程、进程类型、可执行文件路径和整机计数
src/collector.ts       采集器生命周期、请求合并与缓存
src/plugins.ts         从 profile 读取已安装插件及其目录
src/analysis.ts        按需在后台进程内运行 V8 CPU 与堆分析
src/attribution.ts     把分析结果按调用栈归到插件、DSH 模块、垃圾回收
src/metrics.ts         进程分类、CPU 与整机占用计算
src/insights.ts        历史点、抽稀、区间统计、工具进程合并与命名
src/tracking.ts        每个进程的 15 秒趋势与程序启停记录
src/responsiveness.ts  卡顿帧与交互延迟记录
src/controller.ts      共享采样器与可见性管理
src/api.ts             页面到后台路由的请求
src/host.ts            DSH Host API
src/client.tsx         侧栏入口与详情页懒加载
src/page.tsx           详情页
src/now.tsx            此刻：整机占比
src/timeline.tsx       三轨联动趋势与工具进程运行条
src/processes.tsx      进程表
src/details.tsx        进程详情侧栏
src/plugin-section.tsx 插件分区：自带进程与按插件分析
src/spark.tsx          趋势小图
tests/                 单元测试与隔离载体
scripts/               构建、原生验证、浏览器验证与基准
```
